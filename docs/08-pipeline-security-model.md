# 08 · Pipeline security model: identities, secrets, deployment governance (Milestone 6)

## Credential inventory

| Credential | Used by | Stored in | Scope / lifetime | Rotation |
|---|---|---|---|---|
| `GITHUB_TOKEN` | every job | generated by GitHub per job | permissions declared per job, expires at job end | automatic |
| `AUTO_MONITOR_PAT` | CDL verify/secret/misconfig/build, CDP deploy (init.sql) | repo secret (deployment repo) | fine-grained, **read-only** Contents+Actions, **auto-monitor only**, 30-day expiry | regenerate on expiry → `gh secret set` |
| GHCR push/pull | CDL publish / CDP | none — uses `GITHUB_TOKEN` (`packages: write/read`) | job lifetime | automatic |
| Signing identity | attestation | none — OIDC token → Sigstore short-lived cert | minutes | automatic |
| `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD`, `PG_PASSWORD`, `INTERNAL_API_TOKEN`, `JWT_PRIVATE_KEY`, `ENCRYPTION_KEY`, `ADMIN_PASSWORD` | CDP deploy job | **environment secrets** — different values in `staging` and `production` | readable only by a job bound to that environment | rerun `scripts/setup-github.sh` + redeploy |
| AWS access (real setup) | deploy job | none — **OIDC → `auto-monitor-gha-deployer` role** | 1 h, only `environment:production` of this repo | nothing to rotate |
| LLM API keys (real setup) | agent | environment secrets | per env | provider console |

Previously: all in a `.env` file on the server, shared by everyone, never rotated.

## Least privilege — who can do what

| Identity | Can | Cannot |
|---|---|---|
| Developer | push branches, open PRs, run CI | merge to main without review, change CDL/CDP, read env secrets, deploy |
| CI jobs | read code, upload reports | push images, read any secret, write to repo |
| CDL publish job | push images, sign | read production secrets, deploy |
| CDP deploy (staging) | read staging secrets, pull images | read production secrets |
| CDP deploy (production) | read prod secrets — **after approval, from main only** | build images, run unapproved digests |
| Reviewer (environment) | approve/reject production | — (every approval is recorded) |

## Governance controls implemented
* **Protected branches** (`main`, both repos): PR, 1 approval, code-owner review, required check (`CI evidence` / `CDL gate`), no force-push/delete.
* **Pipeline files protected**: CODEOWNERS on `.github/**`; delivery & deployment gates live in a separate repo; policy guard detects weakened gates.
* **Protected environments**: `staging` and `production` deployable from `main` only; `production` requires reviewer approval.
* **Approval**: GitHub environment required reviewer.
* **Audit trail**: Actions run history (who triggered, which commit), environment deployment history (who approved, when), `deployed-<env>.json`, `release-manifest.json`, attestation (who built what).

## Runner security
* CI/CDL run on **GitHub-hosted ephemeral VMs**: fresh per job, destroyed after → no persistence, no cross-project sharing.
* No Docker socket is mounted into containers; builds use the runner's own Docker; no privileged containers.
* Fork PR workflows require maintainer approval; PRs from forks never get secrets.
* If a **self-hosted** runner is used for deployment: dedicated machine, only the deployment repo, only `workflow_dispatch` (never PR code), runner user not in `sudo`, workspace cleaned (`docker compose down`), outbound firewall allow-list (GitHub, GHCR).
* Network: hosted runners have open egress — mitigated by sha-verified tool downloads; limitation documented.

## Traceability requirements for a deployment
Must be answerable from records: **what** (image digests + source commit), **who built** (CDL run + attestation),
**who requested** (CDP actor), **who approved** (environment review), **when**, **where** (environment), **result** (smoke test / rollback).
